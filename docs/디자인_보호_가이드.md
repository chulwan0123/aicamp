# SILVER 디자인 보호 가이드

문서 버전: 1.2
기준일: 2026-08-21

> 운영 기준은 `https://aicamp-sigma.vercel.app`이다. 화면 3 지역·단지·전용면적 검색의 시각 QA 증거는 `design-qa.md`에 기록돼 있다.

## 문서 목적

SILVER의 기능과 데이터 로직을 여러 환경에서 병렬 개발하더라도 현재 구현된 화면이 손상되지 않도록 작업 경계를 정한다. 이 문서는 “기능을 어떻게 붙일 것인가”를 규정하며, 새로운 디자인을 제안하는 문서가 아니다.

## 디자인 기준선

다음 세 가지를 함께 기준선으로 본다.

1. 작업 시작 시점의 `index.html`
2. 작업 시작 시점의 `assets/**`
3. 로컬 주소 `http://127.0.0.1:8789/aicamp/`에서 실제 렌더링된 화면

원격 저장소의 오래된 상태보다 작업 조정자가 지정한 브랜치·커밋과 현재 렌더링 화면이 우선한다. 기준 버전이 서로 다르면 작업을 시작하지 말고 정확한 기준 커밋을 확인한다.

## 최초 진입 계약

- 서비스 루트 주소에 처음 접근하면 반드시 `#start` 스플래시 화면을 표시한다.
- URL에 해시가 없거나 지원하지 않는 해시가 있으면 `#start`로 처리한다.
- 스플래시의 `부모님의 노후 준비를 시작해요` 버튼을 눌러야 `#home`으로 이동한다.
- 저장된 분석 결과, 로그인 상태, 방문 이력이 있어도 기본 최초 진입을 홈으로 우회하지 않는다.
- 알림, 공유 링크 등 명시적으로 유효한 기존 해시가 제공된 경우에만 해당 화면으로 직접 진입할 수 있다.
- 스플래시의 로고, 태그라인, 배경 영상, 그라데이션, 시작 버튼과 영상 재생 속성을 변경하지 않는다.

## 보호 수준

### A. 잠금: 변경 금지

- 로고와 서비스명
- 모든 제목, 설명, 버튼명, 메뉴명, 배지 문구
- 이미지, 아이콘, 영상, Lottie 데이터, 폰트 파일
- 화면과 콘텐츠의 순서
- 색상, 폰트, 글자 크기, 행간, 자간
- 너비, 높이, 여백, 정렬, 라운드, 테두리, 그림자
- 애니메이션 프레임, 재생 순서, 시간, 반복 방식
- 상단 고정 헤더, 8단계 진행 막대, 하단 고정 버튼, 홈·마이 하단 탭
- 모바일과 데스크톱의 레이아웃 전환 방식

### B. 연결 가능: 시각 결과를 바꾸지 않는 로직

- API 요청과 응답 매핑
- 세금·연금·현금흐름 계산 함수
- 입력값 검증과 상태 저장
- 기존 버튼 클릭 이벤트 연결
- 해시 라우팅 보강
- 기존 결과 영역에 계산값 주입
- 카카오 공유, 로그인, 상담 연결을 위한 어댑터
- 오류 로깅, 분석 이벤트, 테스트 코드
- 시각적 영향이 없는 `data-*`, `aria-*` 연결 속성

### C. 사전 승인 필요

- 새로운 문구 또는 문구 변경
- 새로운 색상, 폰트 크기, 아이콘, 에셋, 애니메이션
- 기존 화면의 추가·삭제·순서 변경
- 컴포넌트의 크기나 배치 변경
- 새로운 상태 UI가 기존 패턴으로 해결되지 않는 경우
- 접근성 개선이라도 화면 모양이나 레이아웃이 달라지는 경우

## 현재 화면 구조

현재 해시 라우트는 아래와 같다. 이름과 기존 연결은 보존한다.

| 순번 | 해시 라우트 | 역할 |
|---:|---|---|
| 0 | `#home` | 홈 |
| 1 | `#parents-age` | 부모님 연령 입력 |
| 2 | `#property-count` | 주택 수·각 주택 공동명의 입력 |
| 3 | `#ownership` | 각 주택 도로명·상세주소 입력 |
| 4 | `#address` | 동일 평형 최근 실거래가 확인 |
| 5 | `#property-value` | 취득연도·현재 주택 거주기간 입력 |
| 6 | `#acquisition` | 은퇴 후 희망 지역 입력 |
| 7 | `#preferences` | 상속·거주·긴급도·현금형태·가족합의·월소득 입력 |
| 8 | `#retirement-region` | 1~7단계 입력정보 최종 확인 |
| 9 | `#analyzing` | 분석 중 |
| 10 | `#result` | 결과 요약 |
| 11 | `#tax` | 세금 상세 |
| 12 | `#cashflow` | 현금흐름 상세 |
| 13 | `#downsizing` | 다운사이징 상세 |
| 14 | `#recommendation` | 추천 상세 |
| 15 | `#home-pension` | 주택연금 상세 |
| 16 | `#inheritance` | 상속·증여 상세 |
| 17 | `#my` | 마이 |
| 18 | `#tax-reform` | 세제개편안 안내 |

새 라우트는 기존 배열의 의미와 번호 연결을 깨지 않는 방식으로 추가한다. 기존 화면 번호를 재사용하거나 중간 번호를 임의로 바꾸지 않는다.

`#ownership`처럼 해시 이름과 현재 화면 내용이 일치하지 않는 항목이 있다. 이는 기존 링크 호환을 위한 현재 계약이므로 정리하거나 이름을 맞추지 않는다.

`#start` 스플래시와 `#ai-consulting` 상담은 19개 본 화면 번호와 분리된 오버레이다. 라우트 배열에서 `#home`의 번호가 0이어도 기본 진입 화면이라는 뜻이 아니다. 최초 진입 기본값은 항상 `#start`다.

## 확정된 입력 8단계

입력 흐름은 다음 순서와 묶음을 유지한다.

| 단계 | 화면 내용 | 고정 동작 |
|---:|---|---|
| 1/8 | 아버지·어머니 연령대 | 두 필드를 같은 화면에서 선택 |
| 2/8 | 보유 주택 수·주택별 공동명의 | 1~3채에 따라 명의 필드 동적 생성 |
| 3/8 | 주택별 도로명주소·상세주소 | 선택한 주택 수만큼 필드 생성, 주소 검색 버튼 유지 |
| 4/8 | 동일 평형 최근 실거래가 | 주소 데이터셋의 조회값과 총액 표시 |
| 5/8 | 주택별 취득연도·현재 거주기간 | 취득연도 필드와 거주기간 필드를 같은 화면에 배치 |
| 6/8 | 은퇴 후 희망 지역 | 유무와 시·군·구 선택을 같은 화면에 배치 |
| 7/8 | 부모님 성향·소득 | 상속, 거주, 긴급도, 현금형태, 가족합의, 월소득 입력 |
| 8/8 | 입력정보 최종 확인 | 연령, 주택 수, 주택, 실거래가, 거주, 희망지를 요약 |

### 입력 화면의 상태 계약

- 기존 `radio`와 `select`가 데이터의 원본이다.
- 화면에는 `.select-trigger`가 노출되고 원본 필드는 숨겨진다.
- 모든 선택은 공용 바텀시트에서 이루어지며 선택 후 원본 필드, 트리거 문구, 요약값이 동기화된다.
- `renderPropertyFields()`가 만드는 주택별 공동명의·주소·가격·취득연도 마크업의 구조를 유지한다.
- 주택 수가 바뀌어도 필드 제목, 명의 배지, 주소 입력 순서와 정보 카드가 유지되어야 한다.
- 기능 연결 시 기존 반복 필드 렌더러를 화면 전체 렌더러로 확장하지 않는다.

## 확정된 결과 정보 구조

`#result`의 정보 순서는 아래와 같으며 바꾸지 않는다.

1. 뒤로가기·`분석 결과`·`홈으로`가 있는 상단 바
2. 월 부족액 중심의 결과 상태와 현금흐름 3개 행
3. `AI 컨설팅 받아보기`
4. `가장 먼저 확인해 보세요` AI 추천과 예상액·상세 버튼
5. `전체 결과`
6. 세금
7. 주택연금
8. 매도·다운사이징
9. 임차·금융운용
10. 상속·증여
11. 자주 묻는 질문 4개
12. 하단 고정 `부모님께 카카오톡으로 공유`·`전문가 상담 신청`

### 결과 데이터 연결 계약

- 결과 상태 문장, 주소·평형·실거래가, 생활비·소득·부족액은 기존 노드에 값만 주입한다.
- AI 추천 제목·설명·예상액은 현재 계층을 유지한다.
- 세금 3개 행과 나머지 결과의 핵심 금액은 해당 노드의 `textContent`만 갱신한다.
- 상세 버튼의 `data-go`와 연결 화면을 보존한다.
- FAQ의 `<details>` 구조와 질문·답변·상세 버튼 순서를 보존한다.
- 결과 수치가 길어지면 금액 포맷을 먼저 조정하고 글자 크기나 레이아웃을 바꾸지 않는다.

## 로직 연결 원칙

### 좋은 방식

```js
const resultValue = document.querySelector('[data-result-value]');

async function updateResult() {
  const result = await loadResult();
  resultValue.textContent = formatWon(result.total);
}
```

- 기존 노드를 찾고 값만 갱신한다.
- 계산과 DOM 반영을 분리한다.
- 이벤트 중복 등록을 방지한다.
- 사용자가 뒤로 가거나 새로고침해도 기존 화면 흐름을 보존한다.

### 금지 방식

```js
screen.innerHTML = renderNewScreen(result);
```

- 화면 전체를 문자열로 재생성하지 않는다.
- 서버 응답 HTML로 기존 DOM을 교체하지 않는다.
- 기능 구현 편의를 위해 클래스와 구조를 새 규칙으로 통일하지 않는다.

## 상태별 연결

### 로딩

- 기존 `#analyzing`의 전체 화면 `analysis-background.mp4`, 그라데이션 오버레이와 흰색 중앙 메시지를 재사용한다.
- 현행 5초 전환을 유지한다. 로딩 시간을 바꾸더라도 영상의 `object-fit: cover`, 위치, 재생 속성은 건드리지 않는다.

### 성공

- 기존 결과 상태, AI 추천, 전체 결과 5개, FAQ의 텍스트 자리에서 값만 갱신한다.
- 숫자가 길어지는 경우 먼저 포맷을 조정한다. 글자 크기 축소나 카드 너비 변경은 하지 않는다.

### 오류

- 기존 정보 카드, 바텀시트, 버튼 패턴 중 가장 가까운 것을 재사용한다.
- 새로운 빨간 배너나 브라우저 기본 `alert`를 임의로 추가하지 않는다.
- 별도 오류 UI가 필요하면 먼저 디자인 승인을 받는다.

### 빈 데이터

- 기존 문구를 임의 생성하지 않는다.
- 화면을 숨기거나 구조를 제거하지 않는다.
- 요구사항에 빈 상태 문구가 없으면 담당자에게 문구 승인을 요청한다.

## 신규 페이지 작성 규칙

1. 목적이 가장 가까운 기존 화면을 선택한다.
2. 입력 화면이면 상단 바, 단계 표시, 20px 좌우 여백, 하단 고정 CTA를 재사용한다.
3. 상세 결과면 현재의 평면 섹션, 10px 구분 영역, 1px 항목 구분선, 소형 외곽선 상세 버튼 패턴을 재사용한다.
4. 선택 UI는 기존 선택 버튼 또는 바텀시트를 재사용한다.
5. 홈·마이 계열이면 500px 컨테이너와 하단 탭 패턴을 유지한다.
6. 텍스트 계층과 간격은 `docs/디자인_시스템_명세.md`의 기존 토큰만 사용한다.
7. 신규 화면 때문에 기존 전역 CSS를 바꾸지 않는다. 필요한 규칙은 해당 화면 범위로 제한한다.
8. 기존 선택자와 충돌하지 않는 이름을 사용하되, 현재 명명 방식에 맞춘다.

## 반응형 보호 기준

필수 확인 너비는 다음과 같다.

- 320px: 좁은 모바일
- 375px: 일반 모바일
- 390px: 일반 모바일
- 500px: 서비스 최대 너비
- 501px 이상: 회색 전체 배경 위 중앙 500px 흰색 서비스 영역

각 너비에서 다음을 확인한다.

- 가로 스크롤이 생기지 않는다.
- 고정 헤더와 고정 버튼이 콘텐츠를 가리지 않는다.
- 입력 단계 숫자는 헤더 오른쪽 아래에 유지되고 3px 진행 막대와 겹치지 않는다.
- 안전 영역이 유지된다.
- 홈·마이 탭의 폭과 위치가 유지된다.
- 카드, 영상, 이미지의 비율과 크롭이 동일하다.
- 결과 상단의 `홈으로`와 하단 고정 공유·상담 CTA가 동일한 위치에 있다.
- 한 줄 말줄임과 줄바꿈 위치가 의도치 않게 바뀌지 않는다.
- 탭 화면 자체는 가로로 움직이지 않고 뉴스 레일과 마이 카테고리만 내부 가로 스크롤된다.
- 두 줄 바텀시트 제목의 닫기 버튼은 첫 줄에 정렬된다.
- 홈 소개 문구의 승인된 줄바꿈과 결과·마이 CTA 타이포그래피가 유지된다.

## 변경 전후 점검 절차

### 작업 전

```bash
git status --short
git diff -- index.html assets/
```

기존 diff를 기록한다. 이미 변경된 파일은 사용자 소유 변경으로 간주한다.

에셋 변경 감지를 강화하려면 작업 전후에 임시 체크섬을 비교한다.

```bash
find assets -type f -print0 | sort -z | xargs -0 shasum -a 256 > /tmp/silver-assets-before.sha256
```

### 작업 후

```bash
find assets -type f -print0 | sort -z | xargs -0 shasum -a 256 > /tmp/silver-assets-after.sha256
diff -u /tmp/silver-assets-before.sha256 /tmp/silver-assets-after.sha256
git diff --check
git diff --stat
```

에셋 변경이 담당 요구사항에 없었다면 체크섬 diff는 비어 있어야 한다.
